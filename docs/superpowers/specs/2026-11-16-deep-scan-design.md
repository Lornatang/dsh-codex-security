# Deep Scan orchestration design

## Objective and constraints

Run independent, full-scope DSH security-review workers automatically, persist their results and bounded progress, recover after a host process exits, and produce an honest, compatible parent scan. Preserve the existing manual and standard scan APIs and the previously completed artifact-compatibility work. Do not weaken the user's current filesystem and export protections or silently start unrestricted workers. The npm package remains `@lornatang/dsh-codex-security`.

## Approaches considered

1. Delegate directly with the existing generic subagent tool. This is simple but inherits the parent's unrestricted tools and leaves budgets and recovery to the model; a prompt alone is not an authority boundary.
2. Run a plugin-owned coordinator over the DSH in-process subagent service, enforce a tool guard for specifically identified workers, and persist progress behind operating-system-owned cross-process locks. This preserves DSH's model selection while keeping worker authority and campaign state under the plugin's control. This is the selected approach.
3. Depend on an external Codex CLI or service. This would add separate credentials and a non-DSH execution dependency, so it is not the requested standalone DSH implementation.

## Coordinator and lifecycle

The coordinator starts or rejoins one deep parent. Its durable journal records immutable target binding and scope, the full file inventory and per-file digests, budgets, wall-clock deadline, run identities, run lifecycle, completed child scan IDs, processed outcomes, no-new count, stop reason, errors and parent assembly progress. It is written atomically before and after each externally visible step. Recovery reconciles the journal with completed or unfinished child scans and never treats lost work as a completed review. Once the elapsed deadline or run budget is exhausted it does not start new work, and it records unfinished coverage instead of claiming completion. Automatic Deep scans reject diff targets because the current worktree inventory cannot represent deleted or revision-only files; existing manual diff workflows remain available.

Use the host's `spawn` provider only when it is local, fresh-context, and supports structured results. Each worker receives the same bound target and scope but not prior workers' conclusions. Its prompt requests a complete independent review; its structured result is validated before a separate Standard child scan is recorded and sealed. The DSH structured-output schema uses only its supported subset; the resulting data is then validated against the full artifact contracts. At most `workers` run concurrently; `maxDiscoveryRuns` counts attempts. Process completed runs in a deterministic order when updating `stopAfterNoNew`. Already running workers are canceled or accounted for on stop, timeout, host disposal or explicit cancellation. A failed or interrupted worker is never counted as a clean review.

The parent merges matching target/rule/anchor/instance fingerprints only when the reported locations and dataflow are compatible, retains each worker's provenance, keeps unrelated instances separate, and records all worker coverage and unresolved work. Same-fingerprint findings at different locations or with conflicting dataflow remain unresolved and count as new; they are not silently merged. Findings with different identities also count as new even when they might describe the same issue. Conflicting or missing results produce partial coverage. A successful parent draft is sealed through the existing scan service; target changes or invalid evidence fail closed. If no worker yields a valid completed review, the parent is failed with diagnostics rather than reported clean. A completed zero-finding scan requires at least one complete worker with its own successful, full-content read receipt for every in-scope inventory file; receipts from different workers may not be combined to claim a complete review. Unavailable or oversized files remain deferred. If no worker meets that condition and no findings exist, the parent fails with diagnostics instead of remaining indefinitely running or reporting a clean scan. Receipts prove delivery to the agent, not comprehension or absence of vulnerabilities.

The start tool returns the scan ID and a random recovery claim promptly and exposes status, cancellation and explicit resume. The journal stores only a digest of the claim and the owner's session identity; resuming, canceling or mutating the parent or its managed child scans from another session requires the claim. If a process dies before the claim is delivered, recovery is limited to the original session; an inaccessible orphan must not be taken over without authorization. Existing manual scans retain their current API. The tool adapter forwards the actual DSH execution identity and cancellation signal; a model-supplied session ID is never trusted. Background work must be owned by the plugin's lifecycle and use the DSH subagent activation's supported lifetime. A restart does not fabricate a parent Agent: resume requires a live authorized calling agent. State survives across processes, while unavailable host services fail with an actionable error rather than silently falling back to unsafe delegation.

## Security and concurrency

Install a host tool guard before worker startup. Reserve the in-process activation's child ID and identify the worker before its first turn; deny every tool other than the dedicated read-only worker tools and DSH's scoped `structured_output`, including other scoped tools and program-execution transports. A dedicated native-tool worker preset installs its own inherited guard, so a later cold-resume remains confined; removing the preset or plugin makes resume fail closed. Worker access also requires a live coordinator binding. Restrict worker reads to the bound inventory and scope with pinned directory/file handles; reject traversal, links that escape the target and files whose snapshot changes. Count a full-file receipt only after the DSH tool pipeline accepts the read result; flush receipts before accepting a worker result. Existing service evidence reads for worker-submitted locations must use the same verified file handle, not validate a path and then reopen it. Repository contents are untrusted data. Worker outputs and saved receipts are validated, not executed.

Each campaign has a persistent local SQLite lock database held in an exclusive write transaction. SQLite uses OS locks and releases them when a process dies; the lock database is never unlinked during normal operation. Every shared parent mutation has a cross-process scan lock, and all index read-modify-write operations have a separate global index lock with fresh reads. Lock acquisition is bounded and cancellation-aware. Atomic checkpoint writes occur while the campaign owner holds the lock. On takeover the new process reconciles journal state before starting work. No PID-only stale-lock deletion or lease timeout may allow two live owners. State storage is a trusted local directory on a filesystem with reliable SQLite locking; unsupported locking or a compromised lock path fails closed.

## Verification and release

Exercise real filesystem and process behavior on Windows, Linux and macOS, using deterministic fake model responses at the DSH provider boundary. Tests cover concurrency limits, no-new and run budgets, elapsed time, cancellation, independent scopes, malformed results, denied tools and path escapes, process crash/restart, two competing owners, partial worker completion and target changes. Retain the existing export-race and artifact-compatibility suite. Test the actual DSH registries and activation interface in addition to the fake provider, and verify package contents and reproducible output. Run GitHub CI before a versioned GitHub release and attempt the npm release with the configured account.
